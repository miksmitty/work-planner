Stages

The steps every use case goes through, in order. Stakeholder Triage (0) comes before them: while a use case is there the delivery clock has not started (it is being refined with the submitter before approval). It is still predicted: set the estimated triage weeks on the Stakeholder Triage box (or per use case under "details"), and the plan shows a tentative triage bar followed by the full timeline, ranked behind work already under way. Set each use case's current stage on the Use cases tab or in the Gantt, and earlier stages are skipped. Type a stage's default length in weeks (a fixed timebox). Hover a stage for ◀ ▶ to reorder, ✕ to remove, or ⚙ to make it the engineering stage, whose length is not fixed but comes from the use case's size and the developers available. Any use case can override a stage under "details" on the Use cases tab.

Engineering size

Engineering effort for each complexity level, in developer-weeks: best case · most likely · worst case (weeks of one developer's work). The plan uses the weighted expected value, (best + 4×likely + worst) ÷ 6, shown after ≈. The 50/80/90% dates come from simulating many runs between best and worst case. Complexity is chosen per use case on the Use cases tab.

SME required

How much subject-matter-expert (SME) time each use case needs. Rate every use case High, Medium or Low for SME required: a use case that leans heavily on experts (reviews, data access, domain sign-off) spends more elapsed time waiting on them. Stages marked SME above (hover a stage and click SME to change them) have their length multiplied by the factor for that rating. Stage default lengths assume a light touch, so Low ×1 means no delay, Medium ×1.25 adds a quarter and High ×1.6 adds 60%. On Build, the factor multiplies the developer-weeks of effort instead. A blank rating has no effect, and a length or effort you set yourself under a use case's "details" is used exactly as entered. Only stages you flag are affected, because waiting on experts stretches elapsed time, not developer workload. The factors are assumptions; adjust them to match your experience.

Reuse

How much of a use case's engineering can build on components that already exist (pipelines, connectors, prompts, evaluation harnesses, hosting) from earlier deliveries. Rate each use case High (most of the plumbing exists), Medium or Low; blank means none. The factor multiplies the effort of stages marked REUSE above (Build by default; hover a stage and click Reuse to change), so High ×0.5 halves Build effort, Medium ×0.7 and Low ×0.85. Reuse never removes Build entirely: integration and testing remain. Under a use case's "details", Builds on links it to another use case in this plan: the saving then only applies once that use case's Build has finished, so delivering the foundation first matters. If there's a link but no rating, Medium is assumed. Effort you enter yourself under "details" is used exactly as entered. The factors are assumptions; adjust them to match your experience.

SharePoint links

Base URL of your SharePoint list item page. Any use case without a URL of its own gets a link built as base URL + SharePoint ID (or put {id} in the URL where the ID should go). A URL entered or imported for a specific use case always wins.
